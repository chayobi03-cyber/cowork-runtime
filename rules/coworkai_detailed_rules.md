# Coworkai 프로젝트 — 세부 운영 규칙 (v11)

> 이 문서는 프로젝트 지침(짧은 버전)에서 참조하는 상세 규칙이다. Claude는 audit, agentic 위임,
> MVP School 운영, 구조화 산출물 작업이 실제로 필요할 때 이 문서를 참조한다.

> **source of truth 메모**: 이 문서는 `cowork-runtime` 저장소(https://github.com/chayobi03-cyber/cowork-runtime)의
> `rules/coworkai_detailed_rules.md`가 source of truth다. Claude Projects 지식파일과 내용이
> 다를 경우, 이 저장소 쪽을 최신으로 간주한다(git commit 이력으로 최신성 판단 — 8절 source of truth
> 규칙의 git 버전).

## 1. Audit 점검 항목 (14개)

audit 모드에서는 긍정 평가보다 결함 탐지를 우선하며 다음을 반드시 점검한다.

1. 요구사항 누락
2. 모호한 명세
3. Claude code 임의 구현 가능성
4. 테스트 부족
5. 회귀 테스트 누락
6. schema/config/metadata 정합성
7. 파일·상태·산출물 traceability
8. 라이선스·출처 리스크
9. 운영자 실수 가능성
10. MVP 범위 초과
11. EMC/회로/PCB 관점의 물리적 타당성
12. 실제 엔지니어 업무 감소 효과
13. 인수인계 가능성
14. 다음 패치 우선순위

**11번(물리적 타당성) 참조 기준**: CISPR 32/35, IEC 61000-4 시리즈, MIL-STD-461, FCC Part 15,
KN 32/35(국내) 등 관련 EMC 표준의 한계치·측정조건. 정량 기준이 정해져 있지 않으면 임의로 수치를
확정하지 않고 "기준 미정 — 확인 필요"로 명시한다.

## 2. Agentic Engineering 세부 규칙

### 2.1 자동 실행 가능 범위 / 사전 승인 필요 범위

L0~L3는 개별 작업 단위의 승인 여부를 다루는 라벨이다. 이와 별개로, L0~L3 체계 자체를 언제
재검토·재설계할지는 항상 창엽님의 상위 판단 영역이며 어떤 자율성 수준으로도 위임되지 않는다.

다음에 해당하면 자율성 수준과 무관하게 항상 사전 승인(L0/L1)을 요구한다.
- 원본 데이터·설계 파일 수정 또는 삭제
- 비가역적 작업(덮어쓰기, 배포, 외부 발송, 프로덕션 반영)
- 승인 상태(approval_status 등)의 최종 확정
- 대외 공개 또는 외부 시스템으로의 반영
- audit 결과에 BLOCKER 등급이 남아 있는 상태에서 다음 단계로의 진행

위에 해당하지 않는 읽기 전용 조사, 초안 작성, 로컬/샌드박스 테스트 실행, 기존 산출물 조회 등은
L2(human-on-the-loop)로 처리 가능하며, 실행 후 결과와 판단 근거를 반드시 기록한다.

참고: 이 L0~L3(자율성 수준) 라벨은 GPT 앱 프로젝트의 R0~R3(작업 위험도) 라벨과 방향이 다르다
(L0=가장 보수적, R0=가장 자동허용). 두 프로젝트 간 산출물을 주고받을 때 라벨 의미를 혼동하지 않는다.

### 2.2 에이전트 실패 및 이상 징후 처리

- acceptance criteria 미달 시 자동 재시도보다 실패 위치·원인 보고를 우선한다(kill condition 원칙).
- fabrication 패턴(존재하지 않는 근거 재주장, 점점 정교해지는 세부사항 추가)이 발견되면 즉시
  작업을 중단하고 사람에게 보고한다.
- 동일 오류가 반복(3회 이상)되면 자율 재시도를 중단하고 사람에게 에스컬레이션한다.
- 동일 산출물에 대해 재작업을 반복 요청할수록 다음 출력의 fabrication 위험이 구조적으로 높아진다는
  점을 감안해, 2회 재작업 후에도 미해결이면 재작업 요청을 반복하는 대신 접근 방식 자체를 바꾸거나
  사람이 직접 개입한다.

**카운터 통합**: "동일 오류 3회 반복"과 "동일 산출물 재작업 2회"는 별개 사건을 셀 수 있는 두 개의
독립된 카운터다. 같은 위임 건에서 두 카운터 중 먼저 임계치에 도달하는 쪽을 기준으로
에스컬레이션/접근 전환을 발동한다 — 오류 유형이 매번 달라도 재작업 요청이 2회를 넘었다면 그 자체로
발동 조건이며, 재작업 요청 없이 동일 오류만 반복돼도 3회에서 별도로 발동된다.

### 2.3 위임 시 컨텍스트 전달

- 작업 위임 시 최신 registry/state/config 파일을 반드시 함께 첨부한다. 미첨부 시 구버전 참조로 인한
  회귀 위험이 있다.
- 위임 프롬프트에는 자율성 수준(L0~L3)을 명시한다.

## 3. Human-on-the-loop 감시 규칙

### 3.1 사후보고 체크포인트

human-on-the-loop 작업은 다음을 포함해 보고한다.
- 실행한 작업과 범위
- 사용한 자율성 수준(L0~L3)
- acceptance criteria 충족 여부
- 발견된 이상 징후(있다면)
- 다음 단계에 대한 제안

### 3.2 즉시 보고(에스컬레이션) 기준

사후보고를 기다리지 않고 즉시 알려야 하는 경우:
- fabrication 패턴 발견
- 동일 오류 3회 이상 반복
- kill condition(예: 파싱 성공률 임계치 미달) 도달
- BLOCKER 등급 결함 발견
- 사전 승인 필요 항목(2.1)이 승인 없이 진행되려는 경우

## 4. MVP School — 아이디어 인큐베이션 및 졸업 판정

### 4.1 개념

School은 아이디어를 접수하고, 작게 범위를 자르고, evidence로 증명받아, 다음 세션의 창엽님 본인이
이어받을 수 있으면 졸업시키는 개인용 로컬 운영 체계다. 조직 전체 인수인계가 아니라 본인 재참조용이다.

한 줄 원칙: 적게 쓰고, 빨리 판단하고, 작게 만들고, evidence로 졸업시킨다.

운영 환경: School은 사외에서 시작하고 사외에서 끝난다. 회사 내부망·사내 시스템 반입을 전제하지
않으므로 별도 기밀정보 처리 규칙을 두지 않는다.

### 4.2 운영 흐름

1. Idea Card 작성 (Google Sheets roster에 신규 행 추가)
2. Admit / Hold / Reject 판단
3. 문제 정의
4. MVP 범위 절단 (4.3 기준 적용)
5. MVP Plan 작성 (Plan-first, 승인 전 파일 생성 금지)
6. 냉정 Audit (섹션 1의 14개 항목 + 4.5 BLOCKER 기준)
7. 제한적 구현 또는 검증
8. Evidence / run_report 정리
9. Local Handoff 메모 작성 (4.6)
10. Performance Scorecard 평가 (4.4)
11. Graduate / Needs changes / Hold / Reject 판정
12. 다음 세션에서 이어받기 (roster 상태 갱신)

사람 역할은 Approve / Reject / Needs changes 세 가지로 제한한다. 반복 파일 정리, 반복 테스트 실행,
로그 수동 비교, evidence 수동 작성, 대량 데이터 수작업 검토는 사람이 아니라 AI/Agent가 실행하고
evidence로 증명한다.

**재학 중 항목의 재진입**: 재학 중인 항목이 다음 버전 작업을 시작할 때는 12단계를 처음부터 다시
밟지 않되, 반드시 다음 두 가지를 먼저 확인한다: (1) 4.3.2 재판정 트리거 해당 여부, (2) 4.5 BLOCKER가
열려 있는지 및 열려 있다면 2.1 사전승인 여부. 확인 결과에 따라 다음 중 하나로 진행한다: 트리거
미해당·BLOCKER 없음(또는 승인됨)이면 7단계(제한적 구현 또는 검증)로 진입하고, 4.3.2 재판정 결과
범위가 다시 크다고 나오면 "재분할"(4단계 MVP 범위 절단으로 회귀) 또는 "School 밖 트랙 이관"(4.3.1
참조, 흐름 이탈)으로 처리한다. 이 확인 없이 곧바로 다음 버전 구현을 시작하는 것은 4.3.2·4.5의
사전승인 규칙을 우회하는 것과 같다.

### 4.3 MVP 범위 판정 기준

다음 중 3개 이상 해당하면 범위가 큰 것으로 본다 — 더 작게 잘라야 한다.

1. 기능이 여러 개 섞여 있다.
2. 입력/출력이 한 문장으로 정리되지 않는다.
3. 테스트 기준이 "그럴듯함" 또는 "만족도" 수준이다.
4. UI, DB, RAG, CST batch, approval system, report, deployment를 한 번에 넣으려 한다.
5. 실패했을 때 어느 모듈 문제인지 분리되지 않는다.
6. 외부 서버, 계정, 권한, 대용량 export, 사내 인증이 MVP 초기 필수 조건이다.
7. Local Handoff 메모 한 장만 보고 다음 세션에서 재개하기 어렵다.

**핵심 판정 질문**: 이 MVP를 하나의 입력, 하나의 주요 출력, 하나의 테스트 경로로 설명할 수 있는가?
안 되면 범위가 크다.

**항목 간 비중**: 위 7개 항목은 원칙적으로 동일 비중(3개 이상=크다)으로 카운트한다. 다만 6번(외부
서버·계정·권한·대용량 export·사내 인증이 초기 필수 조건)은 단독으로 해당해도 그 자체로 범위 초과로
본다 — 이는 4.1의 School 운영 전제(사외 시작·사외 종료)와 직접 충돌하기 때문이다. 나머지 6개 항목
사이의 경중은 별도로 두지 않는다.

**Thin Orchestrator 기준**: 여러 기존 모듈을 통합할 때, 목표가 "전체 시스템 완성"이 아니라 "얇은
연결 경로 검증"이면 통합 MVP로 허용한다. 대표 입력 1~3개로 module A→B→C가 순서대로 실행되고
결과·실패위치가 run_report에 남는지만 확인한다. 각 모듈 내부의 대규모 개선이나 신규 구현을 통합과
동시에 하면 범위 초과로 본다. (참고: 동일 프로젝트에서 이 예외가 반복 발동되는 사례가 실제로 쌓이면
별도 기준 신설을 검토한다 — 아직은 관찰 대상.)

### 4.3.1 과소축소(Under-scoping) 방지 기준

4.3은 범위가 큰 경우만 다룬다. 그 반대 실패 — 범위를 지나치게 잘게 쪼개서 필요한 기능·연결·검증까지
함께 빠지는 경우 — 도 동일하게 감시 대상이다. 범위 절단은 복잡성을 줄이는 것이지, 필요한 것을 빼는
것이 아니다.

다음 중 하나라도 해당하면 과소축소로 보고 재검토한다.
- 같은 아이디어가 3회 이상 재분할됐는데 evidence·산출물 진전이 없다 (쪼개기 자체가 반복되는 목적이
  된 상태)
- 쪼갠 결과물이 그 자체로는 독립적 가치가 없고, 오직 "다음 조각을 위한 준비" 단계일 뿐이다 (최종
  목적과 3단계 이상 떨어져 있음)
- 4.3의 "핵심 판정 질문"을 지키려다, Thin Orchestrator 기준에서 이미 허용된 최소 통합 지점(module
  A→B→C 연결 검증)까지 제거했다
- "범위가 크다"고 반려만 하고, 실행 가능한 더 작은 대안을 함께 제시하지 않았다

위에 해당하면 단순 반려 대신 다음 두 가지를 함께 제시한다:
1. 4.3 기준 중 어느 항목에 해당해서 범위가 크다고 판단했는지 구체적으로 명시
2. 그 판단을 유지하면서도 실행 가능한 최소 버전 대안을 제시. 대안이 없다면 "이 작업은 School의
   소규모 절단 방식과 맞지 않고 별도 트랙(정식 프로젝트/스프린트 등)에서 다뤄야 한다"고 명시한다 —
   School이 모든 작업을 담당할 필요는 없다.

**"별도 트랙"의 정의 범위**: "별도 트랙"은 현재 이 프로젝트 내에서 별도로 정의된 체계가 아니다 —
창엽님이 개별적으로 판단해 처리 방식(정식 프로젝트화, 보류, 폐기 등)을 정하며, Claude는 이관
필요성만 판정하고 이관 절차 자체를 대신 설계하지 않는다. 이관 사례가 실제로 3건 이상 쌓이면 그때
별도 기준 신설을 검토한다(5절 사다리 원칙).

### 4.3.2 재학 중 항목의 범위 재판정 트리거

School 재학 중인 항목은 다음 중 하나에 해당하면, 현재 Scorecard 점수나 BLOCKER 상태와 무관하게
4.3 기준으로 강제 재판정한다.
- 동일 항목이 진입 이후 버전이 3회 이상 갱신됐는데 아직 Graduate하지 못했다
- 최초 판정 이후 기능 범위가 실질적으로 늘었다(예: 새 모듈 추가, 새 입력/출력 경로 추가)

재판정 결과 4.3 기준(3개 이상, 또는 6번 단독 해당)에 다시 해당하면, 그 시점부터는 "재분할" 또는
"School 밖 트랙 이관"(4.3.1 참조) 중 하나로 처리하고 기존 버전 이력은 Local Handoff 메모에 사유와
함께 남긴다.

### 4.4 Performance Scorecard (8축, 졸업 판정 전용)

School 졸업 판정에만 사용한다. 일반 audit(섹션 1)와는 별개 체계다.

| 항목 | 가중치 |
|---|---|
| 1. 문제/효과 명확성 | 12% |
| 2. MVP 범위 절단 성능 | 13% |
| 3. AI 실행 가능성 | 13% |
| 4. 검증/evidence 가능성 | 17% |
| 5. Trajectory / 과정 품질 | 12% |
| 6. 로컬 인수인계(다음 세션 이어받기) 가능성 | 15% |
| 7. 안전/오프라인 적합성 | 12% |
| 8. 비용/속도/재사용성 | 6% |

각 항목 100점 만점, 가중 평균으로 최종 점수 산출.

점수 해석

| 점수 | 판정 | 의미 |
|---|---|---|
| 90~100 | Strong Graduate | 바로 이어받아도 됨 |
| 80~89 | Graduate | 경미한 보완 후 졸업 |
| 70~79 | Needs changes | 보완 후 재심사 |
| 50~69 | Hold | 구조 재정리 필요 |
| 0~49 | Reject | 현재 School 대상 아님 |

BLOCKER가 하나라도 있으면 점수와 무관하게 졸업 불가하며, 최종 점수는 최대 69점(Hold)으로 제한한다.

### 4.5 BLOCKER 기준 (School 졸업 게이트)

다음 중 하나라도 있으면 졸업 불가다.
1. 목적과 문제 정의가 불명확하다.
2. 실행 방법이 없다.
3. 테스트 방법이 없다.
4. evidence가 없다.
5. 사람이 반복 작업을 직접 해야 한다.
6. 다음 세션에서 이어받을 수 없다.
7. MVP 범위가 너무 커서 작게 검증할 수 없다.
8. 실패 원인 분리가 불가능하다.
9. Plan 없이 schema/config/metadata/runner/queue/evidence 구조를 바꾸려 한다.

**2.1과의 연동**: BLOCKER는 졸업 판정뿐 아니라 2.1의 사전 승인 규칙과 동일하게 적용된다. BLOCKER가
열린 채로 해당 항목의 다음 버전 작업(구현 계속, 재구현, 범위 확장)을 시작하려면 먼저 사전 승인
(L0/L1)을 받아야 한다. "아직 졸업 안 했으니 2.1 대상이 아니다"는 해석은 허용하지 않는다.

### 4.6 Local Handoff 메모 (본인 재참조용, 1장 원칙)

목적 / 범위 / 제외범위 / 핵심 결정과 근거 / 현재 상태 / 다음 액션. 조직형 승인 문서나 다수 담당자용
항목(역할별 권한, 배포 절차 등)은 포함하지 않는다.

**자기참조 주의**: 이 메모가 "최신 상태"라는 근거를 메모 자기 자신에게 두지 않는다(예: "이 메모가
최신이므로 최신이다" 식 순환 논리). 최신 여부는 roster의 "마지막 업데이트" 필드나 실제 산출물
타임스탬프로 판단한다.

### 4.7 Evidence 검증 방식 (설계 근거)

School은 GPT의 mvp_school/ 처럼 ZIP 패키지·manifest·validator 스크립트를 만들지 않는다. 이유:
Coworkai School은 파일 패키지를 배포하지 않고 대화·Google Sheets 안에서 상태를 관리하므로, 패키지
무결성을 검증할 대상 자체가 없다. 대신:
- Claude가 만든 실제 파일/코드 산출물은 그 자리에서 직접 실행·검증한다(예: bash_tool로 실행, 결과
  재현).
- 외부 AI(GPT/Codex/Gemini) 산출물은 항상 독립 검증한다(값 재계산, 파일 직접 열람 등 — 자기보고를
  그대로 수용하지 않는다).
- evidence는 "이 대화에 남은 실행 로그·재현 결과"가 곧 evidence이며, 별도 evidence 파일 포맷을
  강제하지 않는다.

이 방식이 School 규모(개인 재참조, 파일 패키지 없음)에 안 맞게 되는 시점 — 예: 실제 코드 저장소를
정기적으로 빌드/배포하게 되는 경우 — 이 오면 별도 validator 도입을 재검토한다.

### 4.7.1 독립검증 시 "참고" vs "채택" 구분

외부 AI(GPT/Codex/Gemini) 산출물을 독립검증할 때, 어떤 기법·도구·자료가 Coworkai 운영 원칙(예:
4.3-6 클라우드 계정 의존 금지, evidence-first/자기채점 불인정)에 저촉되는지 판단하려면, 먼저 그
항목이 다음 둘 중 어느 단계에 있는지부터 구분한다.

- **(a) 연구·벤치마크 참고자료 단계**: 조사·비교·기록의 대상일 뿐, 지금 실제로 구축·적용하려는
  것이 아니다.
- **(b) 실제 채택/구현 대상 단계**: 이 Work Package의 실행 인프라나 절차로 그대로 가져다 쓰려는
  것이다.

(a) 단계에서는 운영 원칙 위반 여부를 판정하지 않는다 — 원칙은 (b) 단계(실제 도입 여부를 결정하는
시점)에만 적용한다. "이 자료를 조사·기록했다"는 사실 자체를 "원칙 위반"으로 단정하지 않는다.

**실제 선례**: 2026-07-16 WP-0001 관련 조사에서, CoVe(Chain-of-Verification, LLM 자가검증 기법)와
Provena(클라우드 기반 provenance 시스템)를 둘 다 "Coworkai 원칙 위반"으로 성급히 단정한 사례가
있었다. 재검토 결과 둘 다 (a)와 (b)를 구분하지 않은 동일한 범주 오류였음이 드러났다 — CoVe는
draft 단계 품질개선 기법으로는 문제없고(audit 근거로 self-report를 대체하는 용도로만 불가), Provena도
지금 참고하는 것 자체는 문제없다(실제 인프라로 도입할 때만 4.3-6이 적용되는 조건부 제약). 이
정정이 같은 세션의 1차 자체검증에서도 놓쳤다가 재검토 요청으로 드러났다는 점에서, **독립검증은
한 번으로 끝나지 않고 재검토 요청에 따라 반복될 수 있다**는 것도 함께 확인됐다(2.2의 "동일 오류
반복" 카운터 관점에서도 참고할 사례).

### 4.10 Track 분류 (Main / Research) — cowork-runtime 연동

`cowork-runtime` 저장소의 실행 원칙(Mission/Core Principles/Execution Rules)에서 온 개념을 School
Work Package(= School 재학 프로젝트 단위) 단위로 통합한다.

**용어 매핑**

| cowork-runtime 용어 | Coworkai 대응 개념 |
|---|---|
| Work Package | School 재학중 프로젝트 하나 (Roster의 행 1개) |
| RFC | Idea Card 접수 단계 (4.2의 1~2단계, Admit/Hold/Reject 판단 전) |
| Main Track | 실제 동작에 필요한 것 — 실행 코드, 검증 로직 등 |
| Research Track | 주변 지원 지식 — 도메인 노트, 조사자료, 참고 문서 등 (Main으로 승급 가능) |

**분류 기준**

- **Main Track**: 실제로 실행되는 코드/설정으로, Claude 또는 사람이 직접 실행·재현해서 evidence를
  확보할 수 있는 것. 예: `traceable_emc_agent_system`의 `tools/*.py`, `doc-rag-converter`의
  `app/*`.
- **Research Track**: 그 자체로는 실행되지 않는 참조 지식·조사 자료·도메인 노트. 예:
  `DOMAIN_NOTES/*.md`, 오픈소스 화이트리스트 조사 자료. Main Track에 직접 반영되려면 별도 승인이
  필요하다(아래 "Research → Main 격리 원칙" 참조).

**Research → Main 격리 원칙**

Research Track의 내용(예: EMC 표준 수치, 조사된 라이브러리)은 **Main Track의 실행 로직에 자동으로
흘러들어가지 않는다.** Research Track에서 Main Track으로 반영하려면 2.1의 사전승인 절차를 거친다.

> 실제 선례: traceable_emc v0.4.2 Plan에서 "CISPR/IEC/MIL-STD 등 실제 EMC 표준 수치 기준 적용"을
> 명시적으로 범위 제외하고 "기준 미정" 상태를 유지하기로 결정한 것이, 이 원칙이 도입되기 전부터
> 이미 실무에서 지켜지고 있던 사례다.

**Main/Research 판정 기준 — 점수가 아니라 사실 기반**

Main Track 여부는 Scorecard 점수가 아니라 **"실제로 다른 Main Track 산출물이 이 Work Package를
실행/참조하고 있는가"**라는 사실로 판단한다. Scorecard는 부가 참고 지표일 뿐, 승급/강등의 직접
트리거가 아니다. 이렇게 분리하는 이유: `상태` 필드의 `Graduate`(4.1 — 인수인계 가능 여부)와
`Track`의 `Main`(실제 가동 여부)은 서로 다른 질문이다. 도메인 노트가 evidence를 다 갖춰 Graduate
판정을 받았더라도, 아직 어떤 실행 코드도 그 내용을 쓰고 있지 않으면 Research Track에 남는다 —
Graduate와 Main 승급은 별개 이벤트다.

**승급 (Research → Main)**

이 승급 규칙은 처음부터 독자 실행 가능한 산출물(위 "분류 기준"에서 이미 Main으로 분류된 것,
예: traceable_emc_agent_system 자체)이 아니라 **원래 참조·지원용으로 만들어진 Research 산출물이
나중에 실제로 쓰이게 되는 경우**에 적용한다. 다음 조건을 모두 만족하면 승급한다.
- 4.5 BLOCKER 없음 (4.4 Scorecard Graduate 이상 권장하되 필수 아님 — 참고 지표)
- 다른 Main Track Work Package의 실행 코드/설정이 이 Work Package의 산출물을 실제로 호출·참조하는
  지점이 최소 1개 존재하고, 그 연결을 Claude 또는 사람이 직접 실행해 확인함(evidence 필요)
- 승급 시 Roster의 Track 필드를 Research → Main으로 갱신하고, 승급 근거(어떤 Main Track 산출물이
  무엇을 참조하는지, 확인 방법)를 Local Handoff(4.6)에 기록한다.

**강등 (Main → Research)**

Main Track Work Package를 재감사(4.2 재진입, 4.3.2 재판정 등)했을 때 다음 중 하나에 해당하면
즉시 Research Track으로 강등한다.
- 4.5 BLOCKER가 새로 발견됨
- 이 Work Package를 참조하던 Main Track 산출물이 더 이상 이를 실행/참조하지 않게 됨(연결 단절)

강등 시에도 승급과 동일하게 Roster 갱신 + Local Handoff 기록을 남긴다. 강등은 실패가 아니라
"현재 실제로 가동 중이 아니다"라는 사실 확인일 뿐이므로, School의 Reject 판정과 다르다 — 강등된
항목은 재학 상태(4.2)를 유지하며 다시 승급 조건을 만족하면 언제든 재승급할 수 있다.

**초기값**: 신규 Work Package는 특별한 사유가 없는 한 Research Track으로 시작한다. 처음부터
Main Track으로 분류하려면(예: 이미 검증된 외부 코드를 그대로 가져와 실행하는 경우) 그 사유를 Idea
Card에 명시한다.

**Full Audit / Quick Audit 구분 — 항목 수는 유지, ROI는 빈도·승인무게로만 확보**

기존 ROI 원칙("과도한 자동화·테스트 프레임워크는 거부")은 불필요한 걸 안 만든다는 뜻이지 검증
깊이를 깎는다는 뜻이 아니다. 따라서 **Full Audit(섹션 1의 14개 항목)은 실행 항목 수를 절대
줄이지 않는다.** ROI는 아래 두 지점에서만 확보한다.

- **빈도**: Full Audit은 최초 Main 승급 시 1회가 기본. 재실행 트리거는 새로 만들지 않고 4.3.2
  재판정 트리거(버전 3회 이상 갱신, 기능 범위 확대, Main→Research 강등 후 재승급)를 그대로
  재사용한다. 이 트리거에 안 걸리는 사소한 패치는 **Quick Audit(5항목: ①요구사항누락 ②모호한명세
  ⑦traceability ⑧라이선스출처 ⑬인수인계)**으로 "바뀐 부분만" delta 체크한다.
- **승인 무게**: Full Audit 결과가 나온 뒤, 2.1의 기존 사전승인 트리거(비가역적 작업·외부 반영·
  EMC 물리 판단 등)에 해당하면 L0/L1 사전승인 필수, 해당 안 되면 L2 사후보고로 충분.

**센싱 기준 (재검토 트리거)**

다음 중 하나라도 **2회 발생**(2.2의 기존 임계치 재사용)하면 이 Full/Quick 구분 설계 자체를
재검토한다.
1. Quick Audit(delta 체크)로 넘어간 패치에서, Full Audit이었으면 잡혔을 결함이 사후에 발견됨
2. L2 사후보고로 처리된 승급 건이 사후에 2.1 트리거에 해당했어야 했던 것으로 판명됨(오분류)

이 두 카운터는 4.3.2의 "버전 갱신 횟수"와는 별개 카운터이며, roster에 별도 열을 만들지 않고
발생 시 Local Handoff(4.6)에 즉시 기록하는 방식으로 추적한다(사례가 실제로 쌓이기 전에는 roster
스키마를 늘리지 않는다 — 5절 사다리 원칙).

## 5. 문서화 승격 기준 (사다리)

업무 중 새로운 기준·개념·툴별 판단 근거가 생겼을 때, 지침에 바로 추가하지 않고 다음 사다리로
판단한다.

1. 한 번만 쓸 내용 → 대화/작업 메모에만 둔다.
2. 같은 실수·판단이 2번 이상 반복됨 → 이 지식파일에 새 항목으로 추가할 후보로 본다.
3. 다른 아이디어/작업에도 재사용 가능함 → 가장 가까운 기존 섹션(Audit/Agentic/School 등)에
   통합하거나, 마땅한 섹션이 없으면 신규 섹션을 새로 만든다. 아직 정해진 도메인/개념 전용 섹션은
   없다 — 실제로 3개 이상 쌓이기 전에는 새 섹션을 만들지 않는다.
4. 물리/도메인 검증 기준임 → 섹션 1의 11번(물리적 타당성) 참조기준에 통합한다.
5. School 졸업 판정에 직접 영향 있음 → 4.4(Scorecard) 또는 4.5(BLOCKER) 수정 후보.
6. Claude의 행동방식 자체를 바꿔야 함 → 프로젝트 지침(짧은 버전) 수정 후보. 단, 매우 드물게.

원칙: 배운 것은 버리지 않되, 상위 지침을 계속 키우지 않는다. 지금 규모(지침 1개 + 지식파일 1개 +
roster 1개)에서 별도 노트 파일을 새로 늘리는 것은 실제로 반복이 쌓이기 전까지 보류한다.

## 7. 구조화 산출물 선택 기준

| 조건 | 산출물 | 내용 |
|---|---|---|
| 파일 10개 이상 또는 여러 세션 작업 | artifact registry | 파일별 상태, 버전, 의존관계 |
| 의사결정 여러 번 번복, 이유 추적 필요 | decision log | 결정, 근거, 변경 사유, 대체안 |
| 외부 문서·논문·소스 다수 인용 | source trace table | 출처, 주장, 신뢰도, 적용 여부, 검증 필요 항목 |
| 리스크/미해결 이슈 3개 이상 | issue/risk map | 리스크, 영향도, 대응안, 우선순위 |
| RAG/벡터DB 연동 가능성 명시적 언급, 반복 참조 자료 | RAG chunk plan | chunk 기준, metadata, source_id, section, keyword, linked decision |
| 개념·기술·모듈·테스트·리스크 관계 추적 중요 | knowledge graph | 노드, 관계, 의존성, 근거, 적용 후보 |
| 위 조건 해당 없음 | 없음 | 일반 요약으로 충분 |

구조화 작업은 실제 외부 DB 접근을 전제하지 않고, 현재 Claude 프로젝트에서 가능한 파일·문서·표
형태로 먼저 정리한다. 필요 시 향후 로컬 DB/벡터 DB/그래프 DB/RAG 시스템으로 확장 가능한 형태로
작성한다. 파일 생성은 사용자가 요청했거나 인수인계·재사용·Codex 전달에 실질적으로 도움이 될 때
우선한다.

## 8. 프로젝트 상태 판단 기준

Google Sheet, Google Drive, 외부 서버, 특정 클라우드/SaaS를 필수 전제로 두지 않는다(단, School의
roster 도구 선택은 4.8에서 별도로 확정됨). 현재 대화의 최신 지시, 사용자가 제공한 파일, 업로드된
산출물, 이전 인수인계 자료를 우선한다.

같은 대화 안에서 동일한 registry/state/설정 파일의 여러 버전이 첨부되면 가장 최근 첨부본을 source
of truth로 삼고, 어느 버전 기준인지 답변에 명시한다.

상태가 불확실하면 다음 네 가지로 구분한다.
- 현재 확실한 내용
- 이전 맥락상 추정 가능한 내용
- 확인 필요한 내용
- 다음 상태 요약·인수인계 자료·프로젝트 맥락 패키지에 반영할 내용

여러 프로젝트가 동시에 재학·진행 중일 때는, 새 세션 시작 시 관련 roster/registry 상태를 한 번
훑어 정체되거나 방치된 항목이 없는지 확인한다.

## 9. Google Drive 파일 운영 기준 (PARA 기반)

### 9.1 배경 및 참조 출처

Drive에 프로젝트 산출물(zip, 문서, roster 등)이 시간순으로 계속 쌓이면서 동일 이름 파일 중복,
어느 게 최신인지 불명확한 상태, 판단 보류된 오래된 zip 다수 문제가 실제로 발생함(2026-07-13
roster 5중복 확인이 계기). 다음 두 출처를 근거로 기준을 세운다.

- **Google 공식 가이드**(support.google.com): 검색에만 의존하기보다 단순하고 예측 가능한 폴더
  구조와 일관된 이름 규칙을 우선 권장.
- **PARA Method**(Tiago Forte, *Building a Second Brain*, 2017 최초 발표/2022 저서): Projects·
  Areas·Resources·Archives 4버킷으로 "지금 얼마나 실행 중인가(actionability)" 기준 분류. 특정
  업체 종속 없는 오픈 프레임워크이며 Drive/Notion/Obsidian 등 도구 무관하게 적용 가능.
- 2026년 시점 실무 가이드 공통점: 최상위 폴더 5~7개 이내 유지, 파일명 ISO 날짜(YYYY-MM-DD)
  접두사로 시간순 정렬, 빈 폴더·1~2개짜리 폴더는 탐색만 방해하므로 만들지 않음.

### 9.2 버킷 구조 (Coworkai 규모에 맞춘 3버킷 — Areas는 필요 생길 때만 생성)

PARA 4버킷을 그대로 쓰되, 지금 시점엔 "완료 지점 없는 지속 책임" 항목이 뚜렷하지 않아 Areas
폴더는 실제 항목이 생기기 전까진 만들지 않는다(9.4의 just-in-time 원칙).

| PARA 버킷 | 정의 | Coworkai 대응 | Drive 폴더명 |
|---|---|---|---|
| Projects | 마감/완료 지점 있는 능동 작업 | School 재학중 Work Package(Roster 행 1개, Graduate가 완료 지점) | `Coworkai_유지` |
| Areas | 마감 없이 지속되는 책임 | 예: 저장소 상시 관리 등 — 현재 해당 항목 없음 | `Coworkai_Areas` (미생성 기본) |
| Resources | 아직 실행에 안 쓰이는 참고자료 | 4.10의 **Research Track**과 동일 개념 | `Coworkai_Resources` |
| Archives | 비활성이지만 삭제 안 함, 무기한 보존 | Graduate/Reject 확정 항목, 강등 후 재승급 가능성 낮은 것, 판단 불가한 구버전 산출물 | `Coworkai_Archives` |

### 9.3 버킷 간 이동 트리거 — 신규 규칙 아님, 기존 4.10 재사용

새 이동 규칙을 만들지 않고 4.10의 기존 트리거를 그대로 Drive 폴더 이동 시점으로 연결한다.

- **Resources → Projects/Areas**: 4.10 "승급(Research→Main)" 조건 그대로.
- **Projects/Areas → Resources**: 4.10 "강등(Main→Research)" 조건 그대로.
- **Projects → Archives**: 4.4/4.5의 Graduate/Reject 판정 확정 시.

### 9.4 운영 원칙

1. **Just-in-time**: 폴더는 실제로 넣을 파일이 생겼을 때만 만든다. 미리 만들어두지 않는다 — 실제
   사례: "정리정돈"이라는 이름으로 삭제 후보 모음 폴더를 미리 만들었다가 곧바로 폐기한 시행착오
   (2026-07-13)가 이 원칙의 직접 근거. "지킬 것"을 모으는 폴더(Projects/Resources/Archives)는
   판단 기준이 명확하지만, "지울 것"을 모으는 폴더는 계속 늘어나기만 하고 판단 기준이 없다.
2. 최상위 폴더는 5~7개 이내로 유지한다.
3. 신규 파일부터 `YYYY-MM-DD_설명` 이름 규칙을 적용한다. 기존 파일 일괄 리네임은 하지 않는다
   (ROI — 16인 규모에서 과도한 정리 작업 지양).
4. Archives는 정기 리뷰 대상에서 제외한다(PARA 권장 사항). 8절의 "새 세션 시작 시 roster
   훑어보기"는 Projects(재학중 Work Package)에만 적용되고 Archives에는 적용되지 않는다.
5. **"버킷 밖 = 삭제"가 아니다.** Archives에 있는 것도 삭제 대상이 아니며, 실제 삭제는 별도 판단
   (저장공간 문제 등)이 있을 때만 사람이 직접 실행한다. Claude는 삭제를 자동 실행하지 않는다 —
   2.1의 비가역적 작업 사전승인 규칙과 일치.

### 9.5 도구 제약

Google Drive 연결 도구는 파일 이동(move)·삭제(delete)·이름변경(rename) 기능이 없고 복사(copy)만
지원한다. 따라서 "버킷 이동"은 실제로는 사본을 새 폴더에 만드는 것이며, 원본은 그대로 남는다.
완전한 정리(원본 삭제)는 항상 사람이 Drive UI에서 직접 수행해야 한다. Claude는 이동 대상과 사유를
명확히 제시하고, 사람이 원본 삭제 여부를 최종 결정한다.
