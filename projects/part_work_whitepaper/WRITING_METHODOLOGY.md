# WRITING_METHODOLOGY.md — 백서 작성 방법론

> **구조 안내 (AI/사람 공통 먼저 읽기)**
> 이 문서는 4개 고정 절(A/B/C/D)로 나뉜다. 각 절 제목과 목적은 바뀌지 않는다.
> 새로운 사례·아이디어가 생기면 해당 절의 "근거 항목" 표에 **행을 추가**하기만 하면 된다 —
> 절 제목을 새로 만들거나 문서 구조를 재배치하지 않는다 (Stable Spine 원칙과 동일).
> 각 항목은 `[분류]-[번호]` 형식의 고유 ID를 가지며, 다른 문서(Topic Card, Decision Log)에서
> 이 ID로 인용할 수 있다. 예: "카드 문구는 M-04 원칙을 따름".
> A/B/C는 **왜**(원칙·근거)를 다루고, D는 **Claude가 실제로 무엇을 하는가**(절차)를 다룬다.

## 한 줄 요약 (실행 규칙)

1. 본문(00/01)은 **원칙만** 담고 자주 안 바뀐다. 실제 성장은 Registry/Card에서 일어난다
   (A절 근거).
2. 갱신을 사람에게 강제하지 않는다. 카드를 **기존 업무의 부산물**로 만들고, 입력 방식 자체를
   말하기·보여주기로 낮춘다 (B절, C절 근거).
3. 이 문서 자체도 같은 원칙을 따른다 — 아이디어가 생기면 새 절을 만들지 말고 아래 표에 항목만
   추가한다.
4. **백서 제작 자체가 agentic 방식이어야 한다** (2026-07-12 목표 명확화) — B/C절의 모든 원칙은
   "사람의 반복 입력·기억 부담을 AI가 대신 지는" 방향을 향한다. 이건 완성된 도구가 아니라
   지금부터 적용하는 제작 원칙이다. 장기적으로 이 구조 위에 실제 업무 효율화 agent를 만드는 게
   목표이나(`ROADMAP.md` M3), v1은 agent가 딛고 설 원자화된 구조를 만드는 데 집중한다.

## A. 문서 갱신 원칙 (본문 vs Registry vs Decision Log)

**목적**: 무엇을, 언제, 어디에 갱신할지 정하는 계층 규칙.

**핵심 결론**: 본문(what is) / Registry(evergreen, 계속 자람) / Decision Log(why, 이벤트 발생
시만)의 3계층으로 분리한다. 캘린더 기반 정기 갱신 대신 **트리거 기반**(SECTION_BY_SECTION_
REVIEW.md의 승격 트리거 재사용)으로 갱신한다.

| ID | 근거/사례 | 핵심 시사점 |
|---|---|---|
| A-01 | Evergreen Notes (Andy Matuschak) | 노트는 "완성 선언" 없이 계속 자란다 — Registry는 완료 상태를 강제하지 않음 |
| A-02 | arc42 아키텍처 문서화 | 본문(what is)과 결정기록(why)을 분리, 빈 섹션 있어도 문서 전체 가치는 유지("캐비닛" 비유) |
| A-03 | PARA (Tiago Forte) | actionability 기준 분류, just-in-time 정리(캘린더 대신 필요 시점에) |
| A-04 | GitLab Handbook-first | 단일 진실원(single source of truth) 운영 방식 — 본문의 "요약만" 원칙 근거 |
| A-05 | Diátaxis | 문서 역할 분리(설명/방법/참고) — 본문(설명) vs Card(방법) vs Registry(참고) 구조 근거 |

## B. 조직 채택 저항 최소화 (파트원이 갱신하게 만들기)

**목적**: 강제나 프로세스 추가 없이 사람들이 자발적으로 기록을 남기게 만드는 법.

**핵심 결론**: Fogg 행동모델(B=MAP: Motivation×Ability×Prompt)에서 동기(Motivation)를
설득하려 하지 말고 쉬움(Ability)과 신호(Prompt)를 설계한다. 갱신을 "새 업무"가 아니라
"기존 업무의 부산물"로 만드는 게 핵심.

| ID | 근거/사례 | 핵심 시사점 |
|---|---|---|
| B-01 | Fogg Behavior Model (B=MAP) | 동기는 불안정하고 설계하기 어려움 — 쉬움(Ability)을 높이는 게 더 안정적이고 효과적 |
| B-02 | Tiny Habits (BJ Fogg) | 새 행동을 기존 루틴에 anchor("이거 한 뒤에 저거 한다") — 카드 작성을 정기 회의 등 기존 루틴 뒤에 고정 |
| B-03 | Bubble 사내 도구 채택 사례 (30%→95%) | 전체 공지보다 소수 "챔피언" 지정 + 2주간 짧은 반복 노출이 실제 채택률을 높임 |
| B-04 | "Definition of Done"에 문서 끼워넣기 | 문서 갱신을 "일이 끝났다"의 조건에 자연스럽게 붙이면 별도 의지가 불필요 |
| B-05 | Blameless 문화 원리 | 실패/미완성 기록에 불이익이 있으면 정보 은폐 발생 — 카드에 "안 됨"을 적어도 안전해야 진짜 상태가 모임 |

## C. 입력 방식 자체의 마찰 제거 (Recognition > Recall, 그리고 그 너머)

**목적**: 카드를 "채운다"는 행동 자체의 인지 부담을 줄이는 UX/입력 방식 설계.

**핵심 결론**: 입력 방식은 "빈칸에 새로 쓰기(recall)"에서 "말하기/보여주기(recognition,
그리고 그 이상)"로 갈수록 마찰이 줄어든다. 아래는 마찰이 낮아지는 순서대로 정리한 스펙트럼.

| ID | 근거/사례 | 핵심 시사점 |
|---|---|---|
| C-01 | Nielsen "Recognition rather than Recall" | 사람은 기억해내는 것보다 보고 고르는 게 쉬움 — 카드 필드를 자유서술 대신 선택지 우선으로 |
| C-02 | NN/G 폼 UX 연구 | 불필요한 필드 제거가 거의 모든 경우 완료율을 높임 |
| C-03 | 음성입력(Voice→Card): Stanford/Baidu 받아쓰기 연구 | 모바일 음성이 타이핑보다 약 3배 빠름, 오류율도 낮음. 단 raw transcript는 그 자체로 안 쓰이고 AI 구조화 레이어 필수 ("Capture-First, Filter-Later"). **⚠️ 실제 제약(2026-07-12 검증)**: Claude는 오디오 파일을 직접 듣지 못한다 — 사람이 별도 받아쓰기 앱 등으로 **먼저 텍스트 전사**한 뒤 그 텍스트를 입력해야 함 |
| C-04 | 화면캡처(Screenshot→Card): 반정형 데이터 마이그레이션 사례 (2026-07-12 공유 기사) | 이미 정리된 화면 정보는 재입력 대신 AI가 읽어서 추출하는 게 손으로 옮기는 것보다 우월. 이미지(jpg/png/gif/webp)는 Claude가 업로드 즉시 직접 볼 수 있어 실제로 지원됨(2026-07-12 검증) |
| C-05 | 화면녹화(Screen Recording→Card/Plan): AI SOP 생성 도구 카테고리 (Scribe, Clevera 등) | 실제 작업을 하며 자연스럽게 설명만 하면 단계/예외/판단기준까지 자동 추출 가능 — Level A뿐 아니라 Level B 정보까지 한 번에 확보. **⚠️ 실제 제약(2026-07-12 검증)**: Claude는 동영상 파일을 직접 재생·분석하는 기능이 없다 (지원 확장자 목록에 mp4/mov 등 영상이 없음) — 원리는 유효하나 현재는 영상을 **프레임 스크린샷 여러 장으로 추출한 뒤 이미지로 입력**하는 우회 방식만 가능 |
| C-06 | 캡처 범위 선택 + PC/휴대폰 환경 분리 (2026-07-12 창엽님 컨셉) | 다중 모니터·특정 창 단위로 캡처 범위를 지정해 불필요한 화면 노출을 원천 차단(Export Safety 6~7번과 직결). PC를 분석 메인으로 두고, 휴대폰은 텍스트/음성메모만 우선 지원, 사진·영상은 PC로 옮긴 뒤 분석 |

### C-06 상세 — 캡처 범위 선택 규칙

- 화면캡처·화면녹화 시 **전체 화면이 아니라 원하는 모니터/창/영역만** 선택해서 담는다.
- 다중 모니터 환경에서는 분석과 무관한 모니터(메신저, 메일 등이 떠 있는 화면)를 애초에
  캡처 범위에서 제외한다 — 이는 Export Safety Checklist 6~7번 문항("불필요한 창 정리")을
  **사후 확인이 아니라 캡처 시점에 원천 차단**하는 방식이라 더 안전하다.

### C-06 상세 — PC/휴대폰 환경 분리 규칙

| 환경 | 역할 | 지원 입력 |
|---|---|---|
| **PC (메인)** | 실제 분석·구조화 처리 담당 | 텍스트, 음성(전사본), 화면캡처(범위 선택), 화면녹화(범위 선택) |
| **휴대폰** | 캡처 입구만, 처리는 안 함 | 메모(텍스트), 음성메모 — 우선 지원 |
| 휴대폰 사진/영상 | 즉시 처리 안 함 | PC로 전달 후 PC 환경에서 분석 진행 |

휴대폰에서 사진·영상을 바로 처리하지 않는 이유: 화면 크기·조작 제약으로 캡처 범위를 정교하게
고르기 어렵고, 결과적으로 불필요한 정보가 더 많이 섞여 들어갈 위험이 크다(Export Safety 원칙과
충돌). PC 환경에서 범위를 정해 처리하는 쪽이 C-06의 "범위 선택" 원칙과 일관된다.

### PC 환경에서 실제 지원 여부 (2026-07-12 검증)

"PC를 메인으로 한다"는 원칙이 성립하려면 PC에서 다섯 방식이 실제로 다 되는지 확인이 필요했다.
`file-reading` 스킬의 디스패치 표를 기준으로 확인한 결과는 다음과 같다.

| 입력 방식 | PC에서 실제 지원 | 비고 |
|---|---|---|
| 텍스트 | ✅ 지원 | 기본 |
| 음성 | ⚠️ **조건부 지원** | Claude가 오디오 파일을 직접 듣지 못함. 사람이 먼저 텍스트로 전사한 뒤 입력해야 함 — C-03 "Capture-First"는 "듣기"가 아니라 "받아쓰기 후 붙여넣기"로 재정의 필요 |
| 스크린샷(이미지) | ✅ 완전 지원 | jpg/png/gif/webp는 업로드 즉시 직접 봄 |
| 화면녹화(영상) | ⚠️ **조건부 지원** | 영상 파일 직접 재생 불가. **프레임을 스크린샷으로 추출해 이미지로 전달**하는 우회 방식만 가능 — "녹화 통째로 분석"이 아니라 "핵심 장면 캡처 여러 장"에 가까움 |
| 캡처 범위 선택 | ✅ 지원 (사람이 수행) | 캡처 도구(OS 기본 기능)의 역할이지 Claude 기능이 아님 |

**결론**: 5가지 중 텍스트/스크린샷/범위선택 3가지는 완전 지원, 음성/화면녹화 2가지는 **사람이
한 단계(전사 또는 프레임 추출)를 먼저 거쳐야** 하는 조건부 지원이다. C-03, C-05의 "Claude에
업로드해서 분석"이라는 기존 표현은 부정확했으므로 위 표 기준으로 정정한다.

**입력 방식 스펙트럼** (마찰 낮은 순, 단 처리 부담은 반대로 증가):

```
텍스트 직접 입력 (기존, 가장 익숙하나 recall 부담 큼)
  → 음성 (Capture-First, 구조화는 AI가)
    → 스크린샷 (이미 있는 정보 재활용)
      → 화면녹화 (프로세스 자체 캡처, 가장 깊은 정보 확보하나 처리 부담 최대)
```

**적용 시 필수 안전장치**: C-03~C-05 방식은 전부 회사 내부 정보 노출 위험이 텍스트 입력보다
크다(특히 화면녹화). `EXPORT_SAFETY_CHECKLIST.md`를 반드시 거친 뒤 Registry/Card에 반영한다.

## D. 카드 입력 처리 절차서 (누가 실행해도 동일한 결과가 나오는 이식형 절차)

**목적**: 원본 입력(텍스트/음성전사/스크린샷 등)을 받아 Topic Card로 구조화하는 작업을,
**이 대화의 Claude에게 의존하지 않고** 사람이 직접 손으로 따라 하거나 다른 AI(다음 세션 Claude,
GPT, 다른 LLM 등)에게 그대로 전달해도 같은 결과가 나오도록 절차화한다.

**중요한 전제**: 백서(Part Work Whitepaper) 자체는 School 재학 프로젝트(WP-0001)이며, 지금
이 Coworkai 대화의 Claude가 백서를 실제로 운영하는 주체가 아니다. 이 절차는 **"백서가 실제로
쓰일 때 그 자리의 누군가"**가 읽고 바로 실행할 수 있어야 한다 — 이 대화가 끝난 뒤에도, 다른
사람이나 다른 AI가 이 문서만 보고 똑같이 할 수 있어야 "구현 준비가 됐다"고 말할 수 있다.

**핵심 결론**: 아래 5단계는 수행자(사람/AI 무관)가 항상 같은 순서로 밟는다. 순서를 바꾸거나
생략하지 않는다 — 순서 자체가 재현성(누가 해도 같은 품질)을 담보한다.

| ID | 단계 | 수행자가 하는 일 | 필요한 참조 문서 |
|---|---|---|---|
| D-01 | 원본 형식 확인 | 받은 입력이 텍스트/음성전사/이미지/프레임스크린샷 중 무엇인지 확인. 불명확하면 원출처(창엽님/파트원)에게 먼저 묻는다 | — |
| D-02 | Export Safety 선확인 | 5개(+화면계열 3개) 문항을 원본에 먼저 적용, 하나라도 걸리면 카드화 전에 제거·치환하거나 원출처에 알린다 | `EXPORT_SAFETY_CHECKLIST.md` |
| D-03 | Level A 필드 채움 | 5개 필드(업무명/왜필요/입력/출력/현재문제)를 원본에서 뽑아 채운다. 원문에 명시 안 된 필드는 "추정"으로 표시 | `TOPIC_CARD_TEMPLATE.md` |
| D-04 | 불확실 지점 표시 | 추론한 필드, 원문에 없던 정보를 "확인 필요"로 별도 표시 — Registry에 곧바로 정식 등록하지 않는다 | `PART_REGISTRY/TOPIC_REGISTRY.yaml` (status는 candidate로만) |
| D-05 | 결과 제시 후 대기 | 완성된 카드 초안을 원출처(창엽님/파트원)에게 보여주고, 정식 등록은 확인 받은 후에만 진행한다 | — |

**이식성 확인 기준**: 이 표만 보고 실행할 때, 표 안의 세 참조 문서(Export Safety Checklist,
Topic Card Template, Topic Registry)만 함께 있으면 D-01~D-05를 완료할 수 있어야 한다. 이
셋 외에 "이 대화의 맥락"이나 "Claude와의 이전 대화 기록"이 추가로 필요하면 이식성이 깨진 것
— 그런 의존성이 발견되면 해당 정보를 표나 참조 문서 쪽으로 옮긴다.

**지금 이 대화에서의 역할**: 지금 Coworkai 세션의 Claude는 이 절차서 자체를 **설계·정비**하는

## 새 항목 추가 방법 (이 문서를 갱신하는 법)

1. A/B/C/D 중 어느 절에 해당하는지 판단한다 (문서 갱신 규칙? 조직 채택? 입력 마찰? 카드 입력
   절차?).
2. 해당 절 표에 다음 번호로 행을 추가한다 (예: B절 마지막이 B-05면 다음은 B-06).
3. 절 제목이나 "핵심 결론" 문장은 그대로 두고, 표만 갱신한다. 다만 새 항목이 "핵심 결론"
   자체를 바꿀 만큼 크면(예: 완전히 새로운 원리 발견), Decision Log(추후 산출물)에 그 사유를
   한 줄 남기고 "핵심 결론" 문장을 그때 수정한다.
4. 이 문서 구조 자체(A/B/C/D 분류)가 안 맞게 되는 시점 — 예: 항목이 각 절 10개를 넘어 항목 간
   관계 추적이 필요해지는 경우 — 이 오면 그때 재구조화를 검토한다 (5절 사다리 원칙, 지금은
   아님).
